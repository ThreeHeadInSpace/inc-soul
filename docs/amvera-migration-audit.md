## 1. Текущее состояние проекта

### 1.1. Фактический стек и сборка

**Это не Next.js.** В `package.json` и lockfile нет `next`; нет `next.config.*`, Next API routes, Next server actions и Next middleware. Переносить приложение на Next.js ради Amvera не требуется.

| Компонент | Фактическое состояние |
| --- | --- |
| Node.js | `engines.node = 24.x`; закрепить 24.x также в целевой сборке и runtime |
| UI | React **19.2.8** по lockfile |
| Fullstack | TanStack Start **1.168.60**, Router **1.170.41** |
| Сборка | Vite **8.2.2**, Nitro **3.0.260610-beta** по lockfile |
| БД | `pg` **8.23.0**, обычный PostgreSQL protocol; PGLite — локальный fallback |
| Почта | Nodemailer **10.3.1**, SMTP Яндекса |
| Сохранённая авторизация | Better Auth **1.6.30**, Grok broker; публичный MVP блокирует её |

`package.json`:

- `dev`: wrapper `scripts/with-app-env.mjs` → Vite, `0.0.0.0:8080`.
- `build`: wrapper → `vite build`, затем **`npm run db:migrate`**, затем `scripts/check-preview-print.mjs`.
- `build:dev`: development build; не замена production-сборке.
- `preview`: Vite preview, `127.0.0.1:8081`; не целевой production-процесс.
- `start` отсутствует. `next build` / `next start` неприменимы.
- `typecheck`, `lint`, `test`, browser-regression scripts имеются. Новую сборку и полный набор проверок этот документ не удостоверяет.

В `vite.config.ts` жёстко указан Nitro `preset: "vercel"`, `serverDir: "./server"`, tracing PGLite. Сейчас артефакт ориентирован на `.vercel/output`, а не на самостоятельный Node-сервер. `vercel.json` задаёт `npm ci`, `npm run build` и автодеплой только `pre-prod` / `prod`. Прямых зависимостей `@vercel/*`, Supabase JS SDK, Vercel Blob/KV/Edge Config в manifest нет.

`startup.sh` — запуск dev-процесса из `/workspace` в фоне с логом `/tmp/app-startup.log`; для Amvera production не подходит. `Dockerfile`, `amvera.yaml`, `start` script и `.github/workflows` в текущем дереве отсутствуют. README частично устарел: утверждение об отсутствии backend/env верно для открытого бесплатного режима, но уже существует закрытое тестовое оформление с БД и SMTP.

### 1.2. Серверные точки входа и режимы

| Участок | Поведение |
| --- | --- |
| `src/routes/api/auth/$.ts` | GET/POST Better Auth, но при `FREE_MVP=true` возвращает 404 до импорта auth server |
| `src/lib/free-print-orders.ts` | TanStack `createServerFn`: availability, загрузка PNG, подтверждение корзины, статус, совместимый одиночный заказ |
| `src/lib/orders.ts`, `strips.ts` | Старые операции заказов и кабинета, защищены `authMiddleware`; при FREE_MVP отклоняются |
| `src/lib/auth/middleware.ts` | Middleware server functions; блокирует старый flow, далее проверяет same-site и пользователя |
| `server/middleware/grok-pwa.ts` | Manifest/install page и потоковая вставка HTML head; нужен также вне Vercel |
| Vite plugins | Dev bootstrap PGLite, auth popup, `/__app-env`; production ими заменять нельзя |

`FREE_MVP = true` в `src/lib/pricing.ts`. Открытое приложение собирает фотоленту локально, экспортирует JPEG/PNG и хранит recent/cart в браузере. Закрытое гостевое оформление разрешено, только если одновременно есть `FREE_MVP`, **`VERCEL_ENV=preview`**, реальный PostgreSQL (`dbSource === "neon"`) и достаточно длинный `PRINT_PREVIEW_ACCESS_CODE`. Название `neon` в коде историческое: ветка фактически использует `pg`, независимо от поставщика PostgreSQL. На Amvera без адаптации проверка Preview выключит заказ, хотя сервер и БД могут работать.

### 1.3. Файлы, нагрузка и ограничения

- Canvas/фильтры/композиция работают в браузере. Сервер не требует Chromium, ffmpeg, ImageMagick, GPU или фонового рендера.
- PNG в активном гостевом flow не записывается в файловую систему приложения: Buffer → PostgreSQL → SMTP. Чтение FS есть для metadata/OG, миграций и служебных скриптов. Служебный `print:test-mail` читает файлы и отправляет письмо; это не проверка без побочных эффектов.
- `cart-limits.ts`: **4** разные ленты, до **12** экземпляров позиции, до **24** всего; PNG до **3 300 000 байт**, суммарно **9 000 000 байт** на заказ. Тираж не размножает исходный PNG в БД.
- Загрузка PNG — отдельные последовательные запросы из `FreePrintCheckout.tsx`. Base64 одного максимального файла занимает около **4,4 МБ**, плюс JSON/метаданные и сериализация TanStack. Запросить/проверить лимит body на всей цепочке ingress → Node; стартовая настройка **не менее 6 МиБ**, приложение продолжает проверять свой меньший лимит. Это требование проекта, не подтверждённый лимит Amvera.
- Сервер проверяет PNG signature, chunks/CRC, размер **600×1800**, RGB/RGBA, inflate с ограничением примерно **4,32 МБ**. Распаковка и CRC синхронные, поэтому при параллельных загрузках возможна задержка event loop. Несколько копий base64, строк и Buffer увеличивают RSS сверх размера файла.
- До 9 МБ вложений превращаются примерно в 12 МБ base64 MIME плюс заголовки/переносы; проверять доставку предельного письма на тестовом ящике. SMTP connection/greeting timeout — 10 с, socket timeout — 30 с; **это не общий deadline запроса**. Отправка сейчас выполняется внутри оформления после фиксации заказа.
- Нужны согласованные end-to-end таймауты; ориентир теста HTTP — 90–120 с с ограничением общего времени SMTP. Реальные лимиты ingress Amvera и доступность исходящего TCP/465 не подтверждены и входят в приёмку. Не обещать надёжность длинного запроса только из-за перехода с serverless.

## 2. Совместимость с Amvera

**Перенос без существенной переработки возможен:** один постоянно работающий Node.js fullstack-процесс для frontend SSR, API и статики + отдельный Managed PostgreSQL в том же российском регионе. Деление на микросервисы, отдельный frontend CDN и отдельный backend для MVP не нужно.

| Часть | Оценка |
| --- | --- |
| React, камера, Canvas, локальная галерея/корзина, Web Share | Код переносится; камера и часть Web Share требуют HTTPS и проверки устройств |
| TanStack routes и server functions | Сохраняются; проверить endpoint mapping, POST, cookies/origin за новым proxy |
| PostgreSQL SQL и `bytea` | Совместимы с обычным PostgreSQL; перенастраиваются URL, роли, TLS |
| SMTP | Реализация переносима; требуется проверка сети и размещения всей почтовой цепочки |
| Nitro Vercel preset / launch | Нужна смена целевой сборки и новая команда запуска |
| Preview gates / version label | Нужна независимая от Vercel модель окружений |
| PWA/OG middleware | Сохранить локальные функции, исключить ненужные зарубежные вставки |

Целевой способ: **Amvera приложение с Docker**, Node.js 24, multi-stage build и production command `node .output/server/index.mjs` после переключения на Nitro **`node-server`**. Этот preset есть в установленной версии Nitro; он включает отдачу статики, использует `NITRO_PORT`/`PORT`, `NITRO_HOST`/`HOST`. Сохранить полную `.output` с server/public и traced dependencies. Это проект решения, **сборкой пока не проверен**. [Запуск Nitro на Node.js](https://nitro.build/deploy/runtimes/node).

Порт согласовать явно: например контейнер `3000`, сервис Amvera на `80`, `HOST=0.0.0.0`, `PORT=3000`. TLS завершает ingress Amvera. Встроенное окружение **Node.JS Server** — допустимая альтернатива после проверки Node 24; Node.JS Browser/static hosting не заменит API. В документации Node Server пример использует Node 18, поэтому считать доступность 24 в шаблоне доказанной нельзя. [Node.JS Server](https://docs.amvera.ru/applications/environments/nodejs-server.html).

## 3. Изменения, необходимые для миграции

### 3.1. Обязательные изменения кода и deploy-конфигурации

1. Сделать Nitro target явным: целевой `node-server`; если Vercel нужен в переходный период, сохранить выбираемый build target и исключить его случайное переключение в старом production.
2. Подготовить Dockerfile, `.dockerignore`, `amvera.yaml`, start script. Исключить `.env*`, `.git`, `.vercel`, attachments/artifacts/logs из build context; сохранить необходимые public/PWA/OG assets. Не передавать SMTP и DB secrets в Docker layers, build args и клиентские `VITE_*`.
3. **Разделить build, миграции и проверки внешних сервисов.** `npm ci` + чистая production-сборка должны обходиться без production DB/SMTP. Текущий wrapper охватывает только Vite, последующий migrator читает переменные родительского процесса; перенос env в локальный файл не является безопасным разделением.
4. Выделить однократный migration/release step под отдельной ролью, с проверкой окружения, блокировкой параллельных запусков и без автоматического применения при старте каждой реплики. Сейчас migrator не имеет общей advisory lock и хранит только имена, без checksum.
5. Ввести явные независимые флаги, например `APP_ENV=staging|production` и `PRINT_CHECKOUT_MODE=disabled|preview`. Это **новые предлагаемые** переменные, пока код их не читает. Публичный режим оформления — отдельное решение после privacy prerequisites, не часть простого переноса. Не подменять Amvera ложным `VERCEL_ENV=preview`.
6. При включённом серверном оформлении отсутствие `DATABASE_URL` должно останавливать запуск/готовность; сейчас это молча переводит код в **in-memory PGLite**. Общий preview fallback можно сохранить для разработки.
7. Явно настроить небольшой pool, connection/query timeouts, корректное завершение процесса; readiness проверяет доступность целевой БД без изменения схемы. Liveness не должна вызывать миграции или отправлять почту.
8. Убрать внешний extensions.js, разместить используемые шрифты локально с соблюдением лицензий; проверить и страницу `?install=1`, и middleware, и dev/build plugins. Ограничить внешние ресурсы политикой CSP после проверки совместимости.
9. Добавить управляемую остановку записи для переключения: новые upload/submit и старые endpoints одинаково закрываются на сервере; закрыть только кнопку недостаточно. Остановить retries/cron на время финальной копии.
10. Обновить README и тесты, завязанные на `.vercel/output`, Vercel Preview и метку версии. Сохранить `serverDir` и проверить PWA после смены preset.

## 4. Архитектура PostgreSQL и хранения фотографий

### 4.1. Подключение, схема, зависимости

`src/lib/db.ts` создаёт один `pg.Pool` на процесс с `connectionString: DATABASE_URL`. Никаких Neon HTTP SDK или Supabase REST/RPC в данном пути нет. Названия `createNeonSql`/`DbSource="neon"` не отражают провайдера. По коду невозможно утверждать, используется ли сейчас direct endpoint или Supabase pooler во всех окружениях: это надо сверить в панели без копирования URL в отчёт.

Метаданные существующего проекта: **PostgreSQL 17.11**, 11 public-таблиц, все `0001`–`0007` записаны в `_migrations`. Поля, индексы и ограничения согласуются с просмотренными SQL-файлами; views в public не найдены. Установлены `plpgsql`, `pg_stat_statements`, `uuid-ossp`, `pgcrypto`, `supabase_vault`; наличие расширения не означает зависимость приложения. Рабочий SQL использует стандартные `jsonb`, `bytea`, UUID, timestamptz, массивы, CTE, `ON CONFLICT`, PL/pgSQL. `gen_random_uuid()` доступен в обычном PostgreSQL 17. В просмотренных миграциях нет вызовов Supabase Auth/Storage/Vault или `auth.uid()`.

| Объект | Состав и перенос |
| --- | --- |
| `print_orders` | Родитель заказа, доставка, суммы/тип/статусы, request UUID, consent_at, legacy PNG/JSON/JPEG. Переносить утверждённые необходимые строки со всеми полями |
| `print_order_items` | PNG и options позиций, UUID, количество, FK `order_id → print_orders.id`, unique `(order_id,strip_id)`, product S3, quantity 1–12. Переносить вместе с заказами |

Индексы: `print_orders` PK, unique order_number/request_id, created_at desc, user_id; `print_order_items` PK и composite unique (префикс order_id поддерживает поиск позиций); `print_uploads` PK и created_at; PK у limits/order_seq/history. Legacy `strips` имеет `(user_id,created_at desc)`; auth — индексы user/email, session/token/userId, account/userId, verification/identifier. `print_orders.user_id` **не FK**; `strip_ids` и `additional_strips` также не образуют FK на `strips`. У items FK **без ON DELETE CASCADE**, поэтому удаление заказа требует сначала удалить позиции в транзакции.

В `0003` и `0004` есть операции над `strips`, в `0001` создаются auth-таблицы. Поэтому нельзя просто исключить таблицы из dump, а затем бездумно исполнить все старые файлы на частичной схеме. Нужен проверенный **MVP baseline** из выбранных объектов с отдельным manifest/history: он не должен заявлять выполнение исключённых операций как реально выполненных. Старые SQL не переписывать; будущий migrator должен распознавать выбранную baseline-цепочку. Полный dump структуры тоже нельзя восстанавливать вслепую: он вернёт legacy-таблицы и Supabase-специфичные объекты/права.

### 4.2. Роли и RLS — обязательная адаптация

Все public-таблицы принадлежат `postgres`; эта роль в источнике имеет BYPASSRLS. Для `print_orders`, `order_seq`, `_migrations`, `print_order_limits`, `print_uploads`, `print_order_items` включён RLS без policies, FORCE RLS выключен; доступ PUBLIC и Supabase API-ролей отозван. Owner/BYPASSRLS позволяет текущему серверу работать.

**Простая смена URL на обычную runtime-role может привести к отказам:** GRANT не обходит RLS без policy. Для целевой БД предлагаются отдельная owner/migration роль и runtime-role без superuser/BYPASSRLS/DDL, с явными grants на нужные операции/sequence и policies только для server-role на выбранных таблицах. Это общий серверный доступ, не клиентская пользовательская авторизация. Не давать runtime доступ к миграционной истории на запись, новым legacy-таблицам и административным функциям. Проверить права UPDATE в trigger на orders/order_seq. Запретить лишний CREATE в public, не клонировать глобальные роли и default grants Supabase.

У пяти legacy-таблиц RLS выключен, API-роли имеют широкие grants; повторно подтверждено. Это известная проблема из privacy audit, сейчас не исправлялась. Пустота таблиц не делает такие default grants пригодными для новой инфраструктуры. Не импортировать `anon`, `authenticated`, `service_role`, схемы `auth/storage/vault` и platform extensions без выявленной потребности. До финального manifest дополнительно проверить полный граф зависимостей, memberships/default ACL, custom triggers/functions, scheduler jobs и внешних потребителей: выборочная проверка каталогов не доказывает их полное отсутствие.

### 4.3. Жизненный цикл и надёжность

Родитель и items создаются одной SQL-операцией с CTE; `UNIQUE(request_id)` обеспечивает повтор подтверждения с тем же UUID без второго заказа. Счётчик номера и insert транзакционны. После фиксации заказа удаляются связанные uploads, затем отправляется письмо. **Успех SMTP не является условием существования заказа**. Сбой между этими действиями оставляет восстанавливаемое состояние; источник истины — БД.

Временные загрузки старше суток удаляются только при следующем upload, отдельного расписания нет; без новых запросов они останутся дольше суток. Входящие upload ограничены 120/час, подтверждения — 30/час глобально, а не per-user. Старый single-strip endpoint обходит отдельный upload limiter/очистку перед insert: до публичного запуска его надо ограничить или вывести из эксплуатации. Текущие preview-ограничения не заменяют защиту публичного сервиса.

`notification_status` проходит pending → sending → sent/failed. При остановке процесса между claim и финальным update запись может застрять в **sending**; штатный retry её не подбирает. Нужны timestamps/lease и контролируемое восстановление либо ручная процедура с проверкой доставки. Стабильный Message-ID не гарантирует отсутствия дубля письма при неопределённом SMTP-ответе. Отдельный брокер сообщений для MVP не обязателен.

Автоудаления заказов, PNG и старых limit buckets нет. Сроки и основания удаления принимает владелец по privacy audit; затем реализуется идемпотентная очистка по расписанию, включая письма/вложения/backup, без каскадного удаления неутверждённых данных. Браузерные оригиналы живут в IndexedDB (предел 150 МиБ), recent previews — в localStorage (16 записей); их не переносит серверная миграция. При сохранении **того же HTTPS origin incsoul.ru** они сохранятся в браузере, но тестовый домен их не увидит.

### 4.5. PNG: PostgreSQL или российское объектное хранилище

| Критерий | А: PostgreSQL `bytea` | Б: приватное объектное хранилище в РФ |
| --- | --- | --- |
| Изменения | Минимальные; перенос проверенного guest flow | SDK, credentials, bucket, keys/checksums, retry, загрузка/чтение/удаление, обработка orphan объектов |
| Консистентность | Заказ и PNG в одной транзакции и backup | Нет общей транзакции с PostgreSQL; нужен протокол ready/pending и сверка объектов |
| Цена | Растут DB disk, WAL и backup; нет отдельного сервиса | Обычно лучше для большого объёма, но отдельно оплачиваются storage/operations/traffic по выбранному поставщику |
| Ограничения | Оставить текущие 3,3 МБ/файл и 9 МБ/заказ; DB технический предел не является бизнес-лимитом | Более крупные объекты не снимают текущие HTTP/SMTP/память-лимиты; presigned uploads — новая архитектура |
| Надёжность | Один restore возвращает и данные, и PNG; большой объём замедлит dump/restore | Отдельные политики versioning/backup и синхронизация restore метаданных/файлов |
| Удаление | Транзакционно items → order; физическое освобождение зависит от vacuum, копии остаются в backup/почте | Удалить metadata + объект + версии/реплики по правилам провайдера; нужна защита от orphan и публичных ссылок |
| Доступ | Фото не выставлены отдельным публичным URL | Private bucket, короткие signed URLs или server-only чтение; нельзя сохранять вечный presigned URL как идентификатор |

**Для небольшого MVP выбрать А.** Сейчас в источнике 2 заказа, 2 items, 0 uploads; PNG items — **733 877 байт**, legacy print_png — **184 979 байт**, всего **918 856 байт**. Эти агрегаты не подтверждают, что записи вымышленные. Фотографии не просматривались. Суммарный физический размер 11 public-таблиц с индексами/TOAST — около **1,47 МБ**; это не размер всего кластера и WAL.

Для оценки роста: 100 заказов × предельные 9 МБ ≈ 0,9 ГБ PNG; 1000 ≈ 9 ГБ, до WAL, временных копий, metadata и backup. Планировать запас, мониторить не только число заказов. Начать с DB disk 5–10 ГБ, подтвердив минимальный доступный размер и фактическое потребление кластера. При росте retained PNG до нескольких ГБ или неприемлемом времени backup/restore повторить сравнение Б. Конкретный S3-поставщик и его цены сейчас не выбраны и не оценены как подтверждённые.

### 5.2. Сеть, диск и backup

Приложение и PostgreSQL разместить **в Москве/подтверждённом российском регионе**, в одной внутренней сети. Не считать выбор бренда Amvera выбором российского региона: у провайдера есть и зарубежные площадки. Подтвердить в договоре/панели также backup, логи, поддержку и внешние прокси. [Регионы Amvera](https://amvera.ru/cloud).

DB подключать по внутреннему **RW endpoint из панели**, не RO/случайной read-реплике. Публичный endpoint по умолчанию не нужен. Внутренняя сеть Amvera сама по себе не добавляет шифрование: согласовать server TLS/CA и валидацию для `pg`, не выключать проверку сертификатов глобально. Ingress: HTTPS/443, корректные Host/forwarded headers; исходящие DNS, PostgreSQL в приватной сети, SMTP Яндекса TCP/465, позже ЮKassa HTTPS/443. Подтвердить body/timeouts у ingress. [Сетевая модель Amvera](https://docs.amvera.ru/applications/configuration/network.html).

Приложению не нужен постоянный диск под фото; временные файлы не должны становиться источником истины. Если позже появятся постоянные локальные файлы, использовать назначенный persistent mount, не каталог сборки. На диске приложения оставить запас для зависимостей и предыдущих артефактов, исключить пользовательские файлы из Git.

Требования проекта: включить ежедневные DB-backup, отдельный snapshot перед cutover, защищённую независимую копию в РФ с проверкой восстановления. Предлагаемые владельцу цели: обычный RPO ≤24 ч, RTO ≤4 ч; **для переключения потеря подтверждённых заказов недопустима**, нужна финальная копия после остановки записи. Если RPO 24 ч неприемлем, нужен иной режим резервирования/WAL/PITR после подтверждения поддержки, это не обеспечивается данным планом автоматически.

Документация PostgreSQL описывает 3 ежедневные и 3 ручные копии, отключение расписания после остановки кластера и восстановление в **новый сервис с новым URL**. Специализированная страница обещает глубину 7 дней: условия расходятся, фактическую retention/включение/цену/российское размещение подтвердить у поддержки. Репликация не заменяет backup, наличие backup не доказывает восстановимость. [Бэкапы и восстановление PostgreSQL](https://docs.amvera.ru/databases/postgreSQL.html), [описание Managed PostgreSQL](https://amvera.ru/managedpostgresql).

### Последующее подключение ЮKassa

Архитектурного препятствия Amvera + Node + PostgreSQL не найдено; **готовой интеграции сейчас нет**. Потребуются отдельные платежные записи/идентификаторы, сумма из серверного расчёта, идемпотентный create payment, серверный секрет и сверка статуса. Наличие `status` и денежных полей старого заказа не заменяет платежный автомат состояний.

Нужны исходящий HTTPS к API, публичный POST webhook по HTTPS на **443 или 8443**, TLS ≥1.2. Webhook не должен требовать браузерной сессии/preview-кода и должен допускаться ingress; проверять подлинность через API объекта и/или актуальные IP-правила, сумму/валюту/заказ, обрабатывать дубли транзакционно. Возврат пользователя не является подтверждением оплаты. Ответ 200 — после надёжной фиксации события, тяжёлую печать/SMTP не включать в критический путь webhook. ЮKassa повторяет неполученные уведомления до 24 ч. [Требования к уведомлениям](https://yookassa.ru/developers/using-api/webhooks), [формат API](https://yookassa.ru/developers/using-api/interaction-format).

Будущие server-only `YOOKASSA_SHOP_ID`/`YOOKASSA_SECRET_KEY` — предлагаемые имена для отдельной задачи; сейчас не создавать, в VITE не передавать. Подключение магазина, чеки и условия платного запуска владелец решает отдельно. DNS/постоянный webhook URL и контролируемый retry совместимы с предлагаемой схемой.

## 7. Пошаговый план миграции

**Все действия ниже — будущие, выполняются только после отдельного задания. Изменения production/DNS/данных требуют отдельного разрешения владельца.**

1. **Зафиксировать scope и подготовить инфраструктуру РФ.** Утвердить объекты/строки переноса, режим checkout, окно обслуживания, SMTP-получателя, сроки хранения, backup и бюджет. Создать staging app + отдельную staging БД в РФ, затем production ресурсы; не связывать staging с исходной DB/почтой автоматически.
2. **Подготовить и развернуть тестовую Node 24 сборку.** Реализовать раздел 3, собирать без production secrets, настроить HTTP/HTTPS, readiness/liveness/restart. GitHub webhook staging отслеживает `pre-prod`, production — `prod`, отдельные приложения/секреты/базы. Защитить prod от случайного push; существующие Vercel hooks пока не трогать.
3. **Подготовить целевую схему PostgreSQL.** На временной БД проверить утверждённый MVP baseline и минимальные роли, FK/indexes/trigger/sequence; исключить legacy/platform объекты. Выбрать PostgreSQL **17** совместимого minor, не делать downgrade 17→16; доступную версию подтвердить в панели.
4. **Репетиция переноса.** Сначала только синтетические fixtures. Позже, после разрешения на данные, проверить выборочный dump/restore на утверждённую российскую среду без отправки почты. Защищённые dumps/checksums не складывать в репозиторий, GitHub Actions artifacts, чат или зарубежное временное хранилище.
5. **Настроить env.** Разделить build/runtime/migration secrets; проверить отсутствие production URL в staging. Сохранить публичный checkout disabled, staging preview — только код и вымышленные данные.
6. **Подключить фото.** Вариант А: те же private bytea; не создавать bucket. Сохранить legacy `print_orders.print_png` вместе с items и metadata. Проверить роли чтения для SMTP. Новые PNG остаются в браузере до разрешённого оформления.
7. **Проверить фотоленту.** HTTPS, camera permissions, 3 кадра S3, фильтры, дата/подпись/шрифты, пересъёмка, download, native Share, PNG 600×1800/300 DPI, mobile/tablet и PWA. Только синтетическая камера/изображения и тестовые устройства.
8. **Проверить корзину и оформление.** 1–4 позиции, тиражи, лимиты, плохие PNG, закрытый режим, неверный код, повторы/две вкладки/reload, network interruption, status/retry; parent/items commit вместе, request UUID не дублируется.
9. **Проверить SMTP и PNG.** Только разрешённый тестовый ящик: сеть/TLS/auth, малое и максимальное письмо, MIME/имена/тиражи, PNG hashes. Имитировать SMTP timeout: заказ сохранён, retry контролируется. Отдельно проверить crash в sending и restart.
10. **Проверить безопасность и внешние передачи.** Browser/server network allowlist, отсутствие extensions/fonts/foreign OG/DB/auth запросов; отсутствие секретов в client bundle, body/PD в логах; закрытые auth/старые routes и доступ к фото; backup restore на новый российский сервис. Снять метрики RSS/latency/disk и выбрать окончательные тарифы.
11. **Выполнить финальный перенос и переключить incsoul.ru в утверждённое окно.** Предварительно после разрешения уменьшить DNS TTL и дождаться прежнего TTL. Выполнить write fence/drain ниже; перенести финальную согласованную копию; проверить invariants; подготовить сертификат и домен, затем изменить только нужные DNS-записи. Не трогать MX/SPF/DKIM/DMARC без отдельной необходимости. Запись на новом сервере разрешить только после проверки назначения БД и fencing старых контуров.
12. **Проверить production и завершить переход.** Сначала smoke в закрытом режиме и один согласованный синтетический end-to-end тест; контролировать запись/номера/mail/disk/errors. Зафиксировать приёмку и окно усиленного наблюдения (предлагается 48–72 ч). Удаление старых ресурсов — отдельное подтверждённое действие после сверки и резервной копии.

### Безопасный перенос структуры и данных: проект процедуры

Не выполнять dump командой «весь Supabase целиком». Утвердить manifest: схема orders/items/order_seq/sequence/function/trigger/limits/uploads и согласованная миграционная история; данные — только необходимые заказы/items, legacy PNG и счётчик, плюс выбранные технические записи. Перед финальной выгрузкой повторить агрегатную инвентаризацию, зависимости и версии. Пять пустых legacy-таблиц и platform schemas не включать автоматически; их отсутствие закрепить блокировками кода.

Использовать совместимые `pg_dump`/`pg_restore` клиента PostgreSQL 17, encrypted transport и ограниченные credentials. Архив custom-format; проверить TOC (`pg_restore --list`) и состав до restore, ownership/grants переназначить на целевые роли (`--no-owner`/`--no-acl` в согласованной процедуре), а не копировать postgres/BYPASSRLS. Table-filtered dump **не включает автоматически все внешние зависимости**: function, trigger, sequences/defaults, RLS/policies, типы и FK проверить по manifest отдельно. Не смешивать логический dump с физической копией Supabase.

Схему подготовить из проверенного baseline; данные загрузить с сохранением id/UUID/номеров/timestamps/status. Финальные FK/indexes/trigger включить и проверить после загрузки в пустую цель: **AFTER INSERT trigger не должен перенумеровать импортируемые заказы**. Восстановление исходного trigger после data load безопаснее импорта строк при работающем trigger; не требовать superuser disable-triggers как штатную роль приложения. Восстановить serial sequence и singleton `order_seq` из источника; проверить следующий номер на репетиции, не создавать лишний реальный заказ для проверки.

Проверки в защищённом российском migration job: counts по выбранным таблицам/типам, FK orphan=0, unique request_id/order_number, суммы quantities/PNG bytes и **SHA-256 каждого переносимого PNG**, наличие legacy PNG, состояние sequence/counter, статусы уведомлений и согласованная история. В публикуемый отчёт выводить только итог PASS/FAIL и агрегаты, не адреса/изображения/индивидуальные хеши. После копирования выполнить ANALYZE на цели в разрешённом migration step. Приложение стартует без автопереигрывания старых SQL.

### Как исключить потерю заказов и две пишущие базы

При данном объёме выбрать **короткое окно обслуживания**, а не dual-write/CDC.

1. Зафиксировать все старые точки записи: custom domain, Vercel Production, Preview/pre-prod, прямые deployment URL, ручные mail retry и возможные фоновые задачи. Нельзя предполагать, что production checkout закрыт, значит все источники закрыты.
2. После отдельного разрешения закрыть на сервере **все** новые upload/submit/legacy writes старого контура, остановить автоматические deploy/migration/retry jobs. Старые неизменяемые deployments могут сохранять старый код: дополнительно перекрыть возможность записи их DB-role/соединений согласованным механизмом; простая смена env или DNS этого не гарантирует. До drain не обрывать выполняющиеся операции.
3. Дождаться завершения активных submit/SMTP. Неопределённые ответы проверить по request UUID. Pending корзины остаются у клиента; уведомить о повторе загрузки с тем же UUID после перехода. Временные uploads по умолчанию не переносить; проверить, что нет незавершённых подтверждений. Sending разобрать без слепой повторной рассылки.
4. Получить финальный консистентный snapshot **после quiescence**; восстановить на цели. Не считать утреннюю репетиционную копию финальной. На обеих сторонах до открытия записи проверить одинаковые counts/состав нужных заказов, PNG, номерной счётчик и статусы.
5. Переключить domain, проверить новый backend и новый RW endpoint, затем снять fence **только на российской цели**. Старые серверы при кешированном DNS должны показывать обслуживание/отказ записи, а не принимать заказы в старую БД. Не проксировать фото через зарубежный старый сервер ради «бесшовности».
6. Сохранять клиентский request UUID при повторе. После переноса существующий UUID должен возвращать прежний заказ; отсутствие старых uploads означает повторную загрузку, а не смену UUID.

GitHub используется для исходников и CI без пользовательских данных. Нативный механизм Amvera: вкладка «Репозиторий», GitHub token/webhook и выбранная ветка; push запускает сборку. Привязать каждый проект к одной ветке; `vercel.json` Amvera ветки не ограничивает. Использовать минимальные необходимые разрешения fine-grained token, срок действия, отдельный webhook secret; токены вводит владелец непосредственно в панели. Дополнительный GitHub Actions не обязателен. [Подключение GitHub к Amvera](https://docs.amvera.ru/applications/git/webhooks.html).

### Откат до и после первой новой записи

- **До открытия российской записи:** если сверка/сертификат/маршрут не прошли, не открывать checkout, не удалять source/backup. Отменить переключение либо оставить страницу обслуживания; повторить репетицию. Возобновление иностранного сбора PD не является автоматическим техническим откатом — сохраняются условия privacy audit и решение владельца.
- **После появления новых заказов в РФ:** не возвращать приложение на устаревшую Supabase-копию. Сначала серверный fence новой записи, drain, snapshot целевой БД, учёт всех новых заказов/request UUID. Предпочтительно откатить версию **в Amvera**, сохранив российскую БД и обратно совместимую схему. Не откатывать schema разрушительными down migrations.
- **Если повреждена новая БД:** обслуживание и восстановление в новый российский кластер, смена URL после сверки. Дневной backup может не содержать последние заказы; без WAL/PITR их восстановление не гарантировано. Процедура backup должна соответствовать принятому RPO ещё до запуска. Письма не заменяют полную БД, но помогают сверке владельцем без публикации PD.
- DNS rollback сам по себе не синхронизирует данные. Старый release как fallback допустим только при предварительно проверенной работе с актуальной российской БД/совместимым API и разрешённой географии обработки; по умолчанию такой fallback не подготовлен.

### Отключение старых сервисов

После приёмки и сверки в согласованное окно: отключить Vercel auto-deploy/hooks и все старые endpoints оформления, отозвать DB/SMTP credentials старых deployments, убрать устаревшие доступы/интеграции. Ротацию выполнять так, чтобы новый runtime продолжал работать. Подтвердить, что нет заказов только в старой системе, а все нужные копии в РФ восстанавливаются.

Далее по отдельному разрешению владельца удалить ненужные данные/ресурсы Supabase и Vercel, dumps и журналы с данными; согласовать сроки удаления backup у поставщиков. Не держать иностранную БД бесконечно как «резервный production». Остановка ресурса не подтверждает удаления его копий. Зафиксировать фактическое отключение подписок/начислений и акт/подтверждение удаления в пределах возможностей провайдеров.

### Короткое резюме для владельца

- Переезд **умеренной сложности**: переписывать приложение не требуется, но одного изменения адреса БД недостаточно. В проекте TanStack Start, а не Next.js.
