# Подключение incsoul-stage к PostgreSQL Amvera

Рабочая ветка — `pre-prod`. Сайт, БД и pgAdmin находятся в Moscow-1.
Baseline уже применён по сообщению владельца. Эта подготовка не подключается к
реальной БД, не запускает SQL-миграции, заказы, авторизацию, письма или платежи.

## Что настроить вручную в incsoul-stage

В секретах **сайта incsoul-stage**, не мигратора:

- `DATABASE_URL`: существующий пользователь **incsoulApp**, внутренний hostname
  **cnpg-incsoul-db-stage-rw**, порт **5432**, база **incsoulStage**. Пароль существующий,
  URL-encode при необходимости. Не присылать значение в чат/логи и не записывать в Git.
- `AMVERA_DIAGNOSTICS_TOKEN`: отдельный случайный токен длиной 32–256 символов
  (например, 32 случайных байта в hex). Это не пароль PostgreSQL.

В обычных переменных временно включить **AMVERA_DB_DIAGNOSTICS=1**.
Ни postgres, ни incsoul_migrator для runtime не принимаются. Runtime проверяет
точные host/user/database/port перед созданием пула; дополнительные URL-параметры
кроме sslmode запрещены. Если внутреннее соединение без TLS — допустим
sslmode=disable; при TLS использовать проверяемый сертификат по настройкам кластера,
не отключать проверку сертификата глобально. Публичный POSTGRES-домен не создавать.

Не задавать VERCEL_ENV=preview, PRINT_PREVIEW_ACCESS_CODE, SMTP_USER/SMTP_PASSWORD,
GROK_AUTH_* или BETTER_AUTH_* для открытия функций. Клиентская авторизация по-прежнему
собирается с VITE_AUTH_ENABLED=false; Docker runtime также задаёт этот off-switch.
DATABASE_URL читается только при выполнении
Node-сервера из env; сборка не читает локальные .env и не требует секретов.

## Как проверить через работающий сервер

После обновления сайта и внесения переменных перезапустить **только incsoul-stage**.
Внутри контейнера сайта выполнить:

```sh
node scripts/check-amvera-db.mjs
```

Скрипт входит в runtime-образ Docker. Он берёт токен из env и обращается к
локальному HTTP endpoint сервера; пароль БД и токен в команду не вставляются.
Выводится только один безопасный код, exit code 0 — успех, 1 — неуспех.
Если в Amvera нет доступной консоли контейнера, использовать защищённый HTTP-клиент:
**POST https://<тестовый-домен-сайта>/_internal/db-check**,
заголовок `Authorization: Bearer <токен из секрета>`. В Postman/аналогичном клиенте
хранить токен в секретной переменной. Не передавать его в URL/query, браузерном JS,
скриншотах или общедоступных коллекциях. GET и запросы без корректного токена дают 404.

| Результат | Значение |
| --- | --- |
| 200, `{"ok":true,"code":"DB_READY"}` | PostgreSQL 17 отвечает, БД/роль верны, все 10 таблиц читаемы |
| 503, DB_NOT_CONFIGURED | DATABASE_URL не задан |
| 503, DB_UNAVAILABLE | Некорректная конфигурация/сеть/подключение; проверить секрет, доступность БД и регион |
| 503, DB_IDENTITY_MISMATCH | Сервер сообщил другую БД/роль/login/версию либо повышенные атрибуты runtime |
| 503, DB_SCHEMA_UNAVAILABLE | Не удаётся прочитать нужную таблицу: проверить baseline и grants через pgAdmin |
| 404 / DB_CHECK_FAILED | Диагностика выключена, неверный токен/метод либо запрос не дошёл до endpoint |

Диагностика запускает `BEGIN READ ONLY`, читает имя БД/пользователя/версию/атрибуты
роли из каталогов и `SELECT * ... LIMIT 0` для десяти прикладных таблиц, затем ROLLBACK.
Пользовательские строки не возвращаются. `_amvera_migrations` не читается: у runtime
нет доступа к миграционной истории. Это проверка доступности таблиц, не полный
schema-diff и не проверка оформления заказа. В HTTP/логах нет URL, токенов, внутренних
адресов, значений строк или сырых ошибок PostgreSQL. Endpoint всегда закрыт в
Vercel-сборке и по умолчанию закрыт в Node-сборке до явного включения и токена.

После успешной приёмки выключить AMVERA_DB_DIAGNOSTICS (удалить или поставить 0)
и удалить AMVERA_DIAGNOSTICS_TOKEN. **DATABASE_URL оставить**. Повторный запуск
проверки требует временного включения диагностики и нового токена.

## Соединения и остановка

Node-сборка использует общий ленивый pg.Pool для приложения и диагностики:
максимум **4** соединения на процесс, connect/acquire timeout **3 секунды**,
statement_timeout **3 секунды**, query_timeout **5 секунд**, idle timeout
**10 секунд**, idle-in-transaction timeout **5 секунд**. При нескольких репликах
общий лимит умножается на количество процессов; начинать с одной реплики.
Ошибки фоновых idle-соединений перехватываются и логируются без драйверных деталей.
Ошибка запроса возвращает безопасную ошибку PostgreSQL is unavailable.
PGLite при ошибке подключения не создаётся; без DATABASE_URL Node-сборка также
не использует встроенное хранилище.

Nitro plugin при SIGTERM/SIGINT начинает drain через pool.end(), не заменяя
обработчики HTTP srvx и не вызывая process.exit(). Новые DB-запросы после начала
закрытия отклоняются; повторное закрытие идемпотентно. Также зарегистрирован
Nitro close hook. Активные запросы ограничены таймаутами.
Vercel/dev сохраняют исходную ветку подключения и прежний PGLite fallback.

## Что остаётся закрыто и что нужно дальше

FREE_MVP=true, вход/кабинет/физическая печать закрыты, auth API отдаёт 404,
Node gate не разрешает гостевые заказы даже с DATABASE_URL и ошибочными Preview
флагами. Диагностика не импортирует mailer и не отправляет писем. Схема данных,
baseline, миграционная ветка и Vercel build command не изменяются. Docker по-прежнему
собирает build:node и запускает только Node entrypoint, без migration step.

До переноса основного домена нужны отдельные этапы: реальная stage-проверка DB_READY,
приёмка камеры/PWA по HTTPS и рестартов, согласованный редизайн, отдельная подготовка
авторизации/оформления/SMTP/платежей при необходимости, backup/восстановление,
проверка нагрузки и прав, утверждённый план переключения DNS и отката. incsoul.ru,
production Vercel/Supabase сейчас не переключаются. Новые заказы для проверки БД
создавать не требуется.

## Проверки подготовки

Локально прошли: TypeScript, ESLint (0 ошибок/4 прежних предупреждения), **19 тестов**
(5 runtime/mock + 14 миграционных/контрактных), `npm run build:node` и HTTP smoke
собранного standalone-артефакта. Проверены страницы/статические ресурсы/PWA,
404 без диагностического токена, безопасный 503 при ошибке конфигурации, auth 404,
редиректы закрытых страниц, недоступность checkout при заданном DATABASE_URL,
остановка и повторный запуск. Без DATABASE_URL отдельный probe подтверждает отказ
embedded storage. Закрытие пула/ошибки соединений проверены моками.

`npm run build:vercel:app` и `scripts/check-preview-build.mjs` также PASS:
Vercel output v3/Node 24/PGLite fallback сохранены, release migrations не запускались.
Проверены отсутствие изменений baseline/Amvera YAML/Vercel config и отсутствие
migration steps в Node build/start. Docker Engine отсутствует: новый runtime COPY
CLI проверен по исходникам, Linux image/реальный signal drain с PostgreSQL надо
подтвердить на стенде. HTTP smoke выполнен вне Windows-песочницы из-за ограничений
loopback. Логи — игнорируемые `artifacts/amvera-runtime-*.log`.

Реальная Amvera DB локально не используется: тесты соединений — с моками,
smoke runtime — с заведомо невалидным URL 127.0.0.1:1, который отвергается до
TCP-подключения. Миграционные regression tests работают только в локальном
PGlite/PostgreSQL 18.3 WASM с синтетическими данными. Реальный результат DB_READY
от PostgreSQL 17 ещё предстоит получить владельцу через приложение на Amvera.
